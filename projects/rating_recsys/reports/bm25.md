# 리뷰 검색: BM25, 하이브리드, 순위 결합

질문: 리뷰의 단어·의미 검색이 C5를 보완하는가? 낮은 점수가 검색 표현 때문인지, 순위 결합 때문인지 구분할 수 있는가?

**현재 판단: 기존 C5와 E5 캐시는 유지한다.** 완료한 BM25·리뷰 검색을 추가하거나 교체한 동일 가중 RRF·추가 전처리는 미채택이다. 저장 순위에서 추가 정답보다 기존 정답의 탈락 손실이 컸다. 단어 검색과 E5 의미 검색의 직접 하이브리드는 아직 평가하지 않았으며, VDB 도입에 앞서 기존 캐시를 사용하는 작은 validation 대조를 권한다.

**RRF 계산은 모든 저장 행과 일치했고, 성능 차이는 후보 유지·탈락으로 분해됐다.** 아래 개수는 고유 식당 수가 아니라 사용자–식당 정답 쌍이다. 추가와 손실을 각 사용자의 전체 정답 수로 나눠 평균하면 Recall 차이가 정확히 재현된다.

| 변경과 비교 대상 | 기존 Top-100 정답 탈락 | 이전 Top-100에 없던 정답 유입 | Recall 순변화·paired 95% 구간 |
|---|---:|---:|---|
| C1 → C1+C4 | 195 | 341 | +2.9620%p [+1.9910, +3.9052] |
| C1 → C1+Two-Tower | 340 | 228 | −1.1859%p [−2.2010, −0.2153] |
| C5 → C1+C4+BM25 | 241 | 83 | −2.7827%p [−3.5885, −2.0034] |

BM25 추가의 사용자 평균 유입 +1.2845%p보다 탈락 −4.0672%p가 커서 총 −2.7827%p가 됐다. 이는 **관측한 후보 경쟁의 분해**이며, 텍스트 신호가 약한 근본 원인을 입증한 것은 아니다. Two-Tower 결합은 C5에 추가한 실험이 아니라 LightGCN을 뺀 조건이다. 이를 RRF 결합 하나의 효과로 해석하지 않는다.

리뷰 검색이 아무 새로운 정답도 찾지 못한 것은 아니다. BM25는 C1·C4의 원래 두 Top-100에도 없던 정답 쌍 177개를 찾았지만, 최종 결합 100개에는 그중 55개만 남았다. 위 유입 83개 중 나머지 28개는 원래 두 출처에는 있었지만 C5 절단에서 빠졌던 정답의 재진입이다. 잡음·공통 표현 제거 조건에서도 기존 정답 탈락 242개, 유입 89개로 같은 양상이었다.

BM25 추가의 NDCG@10 차이 +0.000285의 구간 [−0.002521, +0.003340]은 0을 포함한다. Recall 하락을 모든 지표의 하락으로 확대하지 않는다. C5−C4 Recall 차이 +0.1900%p도 구간 [−0.9199, +1.2980]이 0을 포함해 LightGCN 단독보다 항상 우월하다고 단정할 수 없다.

세 출처의 절단 전 합집합은 평균 약 259개다. 미래 정답을 알고 여기서 100개를 고르는 가상 Recall 상한 29.6911%는 실제 RRF 16.6942%보다 높지만, 정답을 미리 아는 **진단용 상한이지 실행 가능한 추천 점수나 개선 보장**이 아니다. 더 큰 후보 예산도 함께 포함한다.

Bootstrap은 사용자 쌍 2,000회, seed 42다. 기존 validation은 모델 선택에도 사용했으므로 이 구간은 탐색적 재검산이며 새 holdout 증거가 아니다. 여러 비교의 다중검정 보정이나 결합 가중치·상수 튜닝은 하지 않았다.

## VDB와 하이브리드 검색은 무엇이 다른가?

| 구성 | 역할 | 우리 프로젝트에서의 의미 |
|---|---|---|
| Lexical/BM25 | 단어 일치·희귀도·문서 길이로 검색 | 메뉴·재료 등 명시적인 표현을 찾는다. Kiwi+BM25는 이미 실험했다 |
| Dense/E5 | 벡터 유사도로 의미가 가까운 문서를 검색 | 기존 E5 프로필 캐시로 직접 cosine 후보 검색을 점검할 수 있다. Two-Tower 점수와는 다른 조건이다 |
| Hybrid | 단어 검색과 의미 검색 결과를 함께 활용 | RRF만 가능한 것이 아니다. 가중 순위·정규화 점수 결합·학습 재정렬도 대안이다 |
| VDB | 벡터·메타데이터 저장, 검색, 필터링을 운영 | 같은 벡터·거리·대상에 대한 정확 검색이라면 DB로 옮겼다는 이유로 순위가 좋아지지 않는다. 근사 검색은 누락도 별도 측정해야 한다 |

Supabase는 Postgres 전문 검색과 pgvector를 결합하는 공식 예제를 제공한다. 다만 예제의 `ts_rank_cd`는 현재 BM25와 같은 점수 함수가 아니며, 영어 분석 설정도 한국어 리뷰에 그대로 적용하면 안 된다. [Supabase 하이브리드 문서](https://supabase.com/docs/guides/ai/hybrid-search).

현재 검증 catalog는 식당 약 4,400개이지 리뷰 9만 개가 아니다. 식당 프로필 단위 pilot은 기존 로컬 행렬의 정확 cosine 검색과 BM25로 시작할 수 있어 VDB 설치가 선행 조건은 아니다. 서비스에서 갱신·동시 요청·필터 관리가 필요해지면 기존 Supabase의 pgvector 등을 검토한다. DB 도입에 따른 실제 속도·운영 비용은 이번에 측정하지 않았다. [pgvector 정확·근사 검색](https://github.com/pgvector/pgvector).

## 현재 리뷰 표현에서 확인한 한계

현재 BM25의 사용자 query는 최근 4점 이상 리뷰 최대 5개의 내용 단어를 중복 제거한 집합이다. 식당 문서는 같은 기준의 리뷰 최대 10개를 이어 붙인다. 단어를 반복해서 언급한 취향 강도·문장 순서·어떤 리뷰가 일치했는지는 검색 표현에 남지 않는다. 낮은 평점 리뷰를 별도 비선호 query로 쓰지도 않는다.

2026-10-09 합성 문장 6개를 실제 Kiwi와 현재 품사 필터로 확인했다. `맵지 않아 좋다`와 `매워 좋다`는 모두 `맵, 좋`, `친절하지 않다`와 `친절하다`는 모두 `친절`, `안 맵다`와 `맵다`는 모두 `맵`이 됐다. `않/VX`, `안/MAG`가 선택 품사에 없기 때문이다. 기존 잡음 정리가 부정어를 보존해도 뒤의 토큰 필터에서 사라질 수 있다. **표현 손실은 확인됐지만 전체 Recall 하락의 원인이나 영향 크기는 검증하지 않았다.** 부정어를 남기는 것만으로 BM25가 부정의 대상을 이해하는 것도 아니다.

이는 BM25 경로의 한계다. E5에는 이 Kiwi 품사 필터를 적용하지 않으므로 E5 추출 오류의 근거로 옮겨 해석하지 않는다. 현재 E5 추출·학습 검토는 [임베딩 리포트](./review_embeddings.md#임베딩-입력-재점검)에 있다.

## 리뷰를 검색 문서로 사용하는 다음 설계

아래는 **미실행 설계**다. 한 번에 모두 바꾸지 않는다.

1. 먼저 현재 사용자·식당 프로필을 유지하고, 기존 BM25를 대조군으로 읽기 전용 E5 cosine과 직접 하이브리드의 C5 밖 정답 회수를 비교한다. Two-Tower가 낮았다는 사실은 raw E5 cosine 검색의 결과를 대신하지 않는다.
2. query 개선을 별도 조건으로 비교한다. 명시적 검색에서는 사용자가 쓴 요청을 사용하지만, 현재 미래 방문 추천 평가에서는 cutoff 이전 리뷰만으로 취향 query를 만들어야 한다. 메뉴·재료·가격·분위기 표현과 부정을 보존하는 방식, 단어 가중치를 각각 검증한다. 미래 방문 식당이나 미래 리뷰로 query를 만들지 않는다.
3. 그다음 필요할 때 리뷰 한 개 또는 의미가 유지되는 짧은 문장 묶음을 문서로 검색하고, `restaurant_id`로 합친다. 식당별 상위 몇 개 리뷰의 점수·일치 근거를 보존하고, 리뷰가 많은 식당에 무조건 유리한 단순 점수 합은 대조한다. 이미 방문한 식당과 본인 리뷰를 후보 근거에서 제외한다.

기존 E5 캐시는 여러 리뷰를 합친 프로필 벡터이므로 개별 리뷰 벡터로 분해할 수 없다. 3번의 리뷰 단위 dense 검색에는 새 임베딩이 필요하다. 우선 소량의 과거 리뷰로 비용과 효과를 확인하고, 전체 재임베딩 여부는 이후 판단한다.

VDB에 리뷰 날짜를 붙이는 것만으로 누수 방지가 끝나지 않는다. 검색 대상뿐 아니라 사용자 query·식당 프로필·BM25 IDF와 평균 문서 길이도 해당 cutoff 이전 정보만 사용한다. 미래 리뷰가 섞인 전체 식당 벡터는 검색 때 날짜 필터를 걸어도 되돌릴 수 없다. 평가용 cutoff별 색인 또는 동등하게 과거만 사용한다고 검증한 검색 구성을 사용한다.

## RRF를 꼭 유지해야 하는가?

RRF는 원점수 대신 각 출처의 순위 점수 `1 / (60 + rank)`를 합친다. 현재 구현은 출처별 동일 가중치이며 각 Top-100를 합친 뒤 다시 100개만 남긴다. 점수 척도를 맞추기 쉽지만 출처별 정확도와 원점수의 확신 차이는 반영하지 않는다. [RRF 공식 정의](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion).

예를 들어 한 출처에서만 1위인 식당의 점수는 약 0.0164, 두 출처에서 각각 20위인 식당은 0.025다. 여러 출처에 등장하는 식당을 우대하므로, 약한 리뷰 검색을 같은 가중치로 추가하면 기존 정답을 밀어낼 수 있다. 반대로 방문 신호를 보완하는 출처라면 이 결합이 도움이 될 수 있다. RRF가 항상 나쁘거나 항상 최선이라는 결론은 아니다.

대안은 validation으로 정한 가중 RRF, 점수를 정규화한 가중 합, 출처별 후보 할당, 각 출처 점수·순위를 피처로 쓰는 재정렬이다. 정규화 없는 BM25 점수와 cosine의 단순 합은 피한다. 공식 구현과 연구에도 가중 점수 결합 대안이 있지만 우리 데이터에서의 개선은 아직 확인하지 않았다. [Linear retriever](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/linear-retriever), [결합 함수 비교 연구](https://arxiv.org/abs/2210.11934).

**권장:** 기존 C5를 교체하거나 약한 리뷰 검색에 자동으로 동일한 표를 주지 않는다. BM25의 추가 정답은 확인했으므로 그 신호를 선택적으로 전달하는 제한된 후보 보충이나 피처 전달을 validation에서 한 조건씩 검증할 수 있다. 기존 E5 피처 LTR도 개선을 확인하지 못했으므로 재정렬에 넘기면 해결된다고 가정하지 않는다.

기존 C5 100개에 리뷰 후보를 추가로 유지하는 설계는 후보 예산 증가다. 이를 K=100의 개선으로 보고하지 않고, 같은 총 후보 수의 baseline과 비교한다. K=100을 고정한 할당·결합은 기존 후보 손실도 함께 측정한다. 후보 구성이 바뀌면 과거 시점의 새 후보로 ranker를 학습해야 하며, 기존 C5 전용 모델을 그대로 적용한 점수를 최종 성능으로 해석하지 않는다.
