## 비교 조건과 검색 방법

사용자 query는 최근 4점 이상 리뷰 최대 5개에서 얻은 단어 집합이다. 식당 문서는 같은 기준의 리뷰 최대 10개를 연결한다. Kiwi로 형태소를 분석하고 BM25로 단어 일치·희귀도·문서 길이를 점수화한다. 사용자 단어 중복은 제거하고 식당 문서의 반복 빈도는 유지한다.

1. Snapshot

   - `e7896add5b4b5939`

2. 입력 cutoff

   - Validation: 2025-12-19까지
   - Test: 2026-05-04까지

3. 본문 선택

   - 4점 이상
   - 사용자 최대 5개
   - 식당 최대 10개
   - 리뷰당 최대 240자

4. 검색·결합

   - K=100
   - seed 42
   - C5: C1 공동 방문 + C4 LightGCN RRF

5. 추가 전처리

   - 리뷰 선택은 고정
   - 잡음 정리와 공통 표현 제거만 변경

6. 실행 비용

   - 로컬 CPU
   - API 비용 $0
   - 최초 전체 후보 비교 약 87.1초

검색 대상뿐 아니라 query·식당 프로필·BM25 IDF와 평균 문서 길이도 cutoff 이전 자료로 만든다. BM25에는 E5 프로필의 500토큰 제한이 없으므로 두 검색 방식만 바꾼 엄격한 입력 대조는 아니다. 후보 검색 평가이며 새 후보용 LambdaRank는 학습하지 않았다.

## 저장 순위로 확인한 결합 손실

2026-10-09에는 **새 학습·검색 없이 validation 저장 순위만 재계산**했다. 입력 cutoff는 2025-12-19, query 1,645명 중 정답이 있는 1,639명이다. snapshot·cutoff·사용자 이력·개인별 relevance가 BM25와 Two-Tower에서 일치함을 확인했다. 과거 BM25의 ranker 모드는 prefix지만 이 비교에서는 ranker를 학습하지 않았다.

| 후보 조건 | Validation Recall@100 | 후보 순서 NDCG@10 |
|---|---:|---:|
| C1 공동 방문 | 16.5149% | 0.021895 |
| C4 LightGCN | 19.2869% | 0.020708 |
| C5: C1+C4 RRF | 19.4769% | 0.023311 |
| Two-Tower 단독 | 9.4419% | 0.011803 |
| C1+Two-Tower RRF: C4 교체 | 15.3290% | 0.018813 |
| BM25 단독 | 4.5379% | 0.003499 |
| C1+C4+BM25 RRF: 출처 추가 | 16.6942% | 0.023597 |

**RRF 계산은 모든 저장 행과 일치했고, 성능 차이는 후보 유지·탈락으로 분해됐다.** 아래 개수는 고유 식당 수가 아니라 사용자–식당 정답 쌍이다. 추가와 손실을 각 사용자의 전체 정답 수로 나눠 평균하면 Recall 차이가 정확히 재현된다.

| 변경과 비교 대상 | 기존 Top-100 정답 탈락 | 이전 Top-100에 없던 정답 유입 | Recall 순변화·paired 95% 구간 |
|---|---:|---:|---|
| C1 → C1+C4 | 195 | 341 | +2.9620%p [+1.9910, +3.9052] |
| C1 → C1+Two-Tower | 340 | 228 | −1.1859%p [−2.2010, −0.2153] |
| C5 → C1+C4+BM25 | 241 | 83 | −2.7827%p [−3.5885, −2.0034] |

BM25 추가의 사용자 평균 유입 +1.2845%p보다 탈락 −4.0672%p가 커서 총 −2.7827%p가 됐다. 이는 **관측한 후보 경쟁의 분해**이며, 텍스트 신호가 약한 근본 원인을 입증한 것은 아니다. Two-Tower 결합은 C5에 추가한 실험이 아니라 LightGCN을 뺀 조건이다. 이를 RRF 결합 하나의 효과로 해석하지 않는다.

리뷰 검색이 아무 새로운 정답도 찾지 못한 것은 아니다. BM25는 C1·C4의 원래 두 Top-100에도 없던 정답 쌍 177개를 찾았지만, 최종 결합 100개에는 그중 55개만 남았다. 위 유입 83개 중 나머지 28개는 원래 두 출처에는 있었지만 C5 절단에서 빠졌던 정답의 재진입이다. 잡음·공통 표현 제거 조건에서도 기존 정답 탈락 242개, 유입 89개로 같은 양상이었다.

BM25 추가의 NDCG@10 차이 +0.000285의 구간 [−0.002521, +0.003340]은 0을 포함한다. Recall 하락을 모든 지표의 하락으로 확대하지 않는다. C5−C4 Recall 차이 +0.1900%p도 구간 [−0.9199, +1.2980]이 0을 포함해 LightGCN 단독보다 항상 우월하다고 단정할 수 없다.

세 출처의 절단 전 합집합은 평균 약 259개다. 미래 정답을 알고 여기서 100개를 고르는 가상 Recall 상한 29.6911%는 실제 RRF 16.6942%보다 높지만, 정답을 미리 아는 **진단용 상한이지 실행 가능한 추천 점수나 개선 보장**이 아니다. 더 큰 후보 예산도 함께 포함한다.

Bootstrap은 사용자 쌍 2,000회, seed 42다. 기존 validation은 모델 선택에도 사용했으므로 이 구간은 탐색적 재검산이며 새 holdout 증거가 아니다. 여러 비교의 다중검정 보정이나 결합 가중치·상수 튜닝은 하지 않았다.

## 현재 리뷰 표현에서 확인한 한계

| 확인한 한계 | 의미와 적용 범위 |
|---|---|
| 사용자 query의 단어 중복 제거 | 반복 언급의 취향 강도·문장 순서·어느 리뷰가 일치했는지는 남지 않음 |
| 4점 이상 리뷰만 선택 | 낮은 평점 리뷰를 별도 비선호 query로 사용하지 않음 |
| v1의 부정 표현 삭제 | 반대 의미 문장이 같은 토큰이 되는 사례 확인; v2에서 삭제를 수정했으나 Recall 영향은 미검증 |
| v2도 단어 집합 검색 | 부정 표현을 보존해도 그 대상·범위까지 이해하는 것은 아님 |

2026-10-09 실제 Kiwi와 v1 품사 필터에서 `맵지 않아 좋다`/`매워 좋다`는 모두 `맵, 좋`, `친절하지 않다`/`친절하다`는 모두 `친절`, `안 맵다`/`맵다`는 모두 `맵`이 됐다. `않/VX`, `안/MAG`가 선택 품사에 없었기 때문이다.

이는 BM25 경로의 문제다. E5 원문에는 이 품사 필터를 적용하지 않으며, 별도의 [임베딩 입력 점검](./review_embeddings.md#임베딩-입력-재점검)을 따른다.

## 부정 표현 보존 수정 (2026-10-12)

현재 품사 필터는 `안·못·없이·않·못하·말·아니`를 어간과 품사로 선별 보존한다. `없`은 기존 형용사 품사에 포함된다. 실제 Kiwi 회귀 테스트에서 반대 의미 9쌍을 baseline·clean·clean_stopwords 모두의 사용자 query와 식당 색인에서 구별했다.

세 전처리의 profile version을 v2로 올렸다. 기존 v1 색인과 아래 과거 성능 수치는 수정 효과를 포함하지 않으며, 새 색인을 만들어야 변경이 적용된다. 이번 검증은 부정 표현의 삭제 방지에 한정하며, 부정의 대상·범위를 이해하거나 추천 성능이 개선됐다는 증거는 아니다. 실데이터 재검색·test 평가는 수행하지 않았다.

## RRF 유지 여부

RRF는 각 출처의 순위 점수 `1 / (60 + rank)`를 합친다. 현재는 동일 가중치로 각 Top-100을 합친 뒤 다시 100개를 남겨, 여러 출처에 등장하는 식당을 우대한다. 한 출처의 1위는 약 0.0164, 두 출처의 각 20위는 0.025다. [RRF 정의](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion).

점수 척도를 맞추기 쉽지만 출처별 정확도와 원점수의 확신 차이는 반영하지 않는다. 이번에는 약한 리뷰 출처를 더하면서 기존 정답이 밀려났다. 그렇다고 모든 RRF 결합이 나쁘다는 뜻은 아니다.

| 후속 대안 | 비교할 때 지킬 조건 |
|---|---|
| 가중 RRF·정규화한 점수 결합 | validation에서 한 조건씩 비교; BM25와 cosine 원점수를 그대로 더하지 않음 |
| 출처별 후보 할당 | 같은 총 K에서 추가 정답과 기존 정답 탈락을 함께 측정 |
| 후보 예산 확대 | K=100 개선으로 보고하지 않고 같은 큰 K의 baseline과 비교 |
| 검색 점수를 전달하는 재정렬 | 현재 retrieval 후속 범위에서는 보류; 후보가 바뀌면 해당 과거 후보로 ranker도 재학습 필요 |

가중 결합의 효과는 아직 검증하지 않았다. 이후 E5의 quota·RRF는 [다중 벡터 실험](./review_embeddings.md#리뷰별-다중-벡터-후보-검색)에서 비교했지만 C5 보완 이득을 확인하지 못했다. 재정렬에 넘기면 해결된다는 보장도 없다. [점수 결합 구현](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/retrievers/linear-retriever), [결합 함수 연구](https://arxiv.org/abs/2210.11934).

## 리뷰 검색 문서의 후속 설계

현재 후속 범위는 전체 catalog에서 후보를 찾는 retrieval이다. 다음은 **BM25 후속에서 아직 실행하지 않은 비교**다.

1. v2 색인을 만들고 동일 조건의 v1 저장 결과와 비교해 부정 표현 보존의 영향을 확인한다. 새 코드가 곧 성능 개선을 뜻하지 않는다.
2. 같은 사용자·식당 프로필에서 BM25와 E5의 직접 하이브리드를 비교한다. C5 밖 정답 회수와 기존 정답 탈락을 함께 측정한다.
3. 메뉴·재료·가격·분위기·부정을 보존하는 query와 단어 가중치를 한 요인씩 비교한다. query는 cutoff 이전 리뷰에서만 만들고 미래 식당·미래 리뷰를 넣지 않는다.
4. 리뷰·짧은 근거 단위 검색을 식당 단위로 합칠 때 리뷰 수 편향과 중복 근거를 통제한다. 방문 식당과 본인 리뷰를 후보 근거에서 제외한다.

과거 concat E5 캐시는 리뷰별 벡터로 분해할 수 없다. 이후 별도의 리뷰 블록 bank로 평균·Top-3 matching·학습형 late 검색을 실제 수행했으므로, 리뷰 단위 검색 전체가 미실행인 것은 아니다. 입력 정책과 완료 결과는 [임베딩 리포트](./review_embeddings.md#리뷰별-다중-벡터-후보-검색)를 따른다.

날짜 메타데이터만 붙여서는 미래 리뷰가 섞인 식당 벡터를 복구할 수 없다. 평가에는 cutoff별 색인 또는 동등하게 과거 입력만 쓴다고 검증한 구성이 필요하다.

## VDB와 하이브리드 검색의 차이

| 구성 | 역할 | 우리 프로젝트에서의 의미 |
|---|---|---|
| Lexical/BM25 | 단어 일치·희귀도·문서 길이로 검색 | 메뉴·재료 등 명시적인 표현을 찾는다. Kiwi+BM25는 이미 실험했다 |
| Dense/E5 | 벡터 유사도로 의미가 가까운 문서를 검색 | 벡터 cosine 검색. 이후 E5 평균·matching 검색도 실행했으며 Two-Tower 점수와 구분한다 |
| Hybrid | 단어 검색과 의미 검색 결과를 함께 활용 | RRF만 가능한 것이 아니다. 가중 순위·정규화 점수 결합·학습 재정렬도 대안이다 |
| VDB | 벡터·메타데이터 저장, 검색, 필터링을 운영 | 같은 벡터·거리·대상에 대한 정확 검색이라면 DB로 옮겼다는 이유로 순위가 좋아지지 않는다. 근사 검색은 누락도 별도 측정해야 한다 |

Supabase는 Postgres 전문 검색과 pgvector를 결합하는 공식 예제를 제공한다. 다만 예제의 `ts_rank_cd`는 현재 BM25와 같은 점수 함수가 아니며, 영어 분석 설정도 한국어 리뷰에 그대로 적용하면 안 된다. [Supabase 하이브리드 문서](https://supabase.com/docs/guides/ai/hybrid-search).

현재 검증 catalog는 식당 약 4,400개이지 리뷰 9만 개가 아니다. 식당 프로필 단위 pilot은 기존 로컬 행렬의 정확 cosine 검색과 BM25로 시작할 수 있어 VDB 설치가 선행 조건은 아니다. 서비스에서 갱신·동시 요청·필터 관리가 필요해지면 기존 Supabase의 pgvector 등을 검토한다. DB 도입에 따른 실제 속도·운영 비용은 이번에 측정하지 않았다. [pgvector 정확·근사 검색](https://github.com/pgvector/pgvector).

## RAG와 multi-stage 추천에서 공유할 방법론

후보를 찾고 제한된 후보를 더 정밀하게 비교하는 방법론은 공유할 수 있다. E5는 텍스트 표현, C1/LightGCN→LambdaRank는 추천 구조이며, 검색 원문을 생성 모델에 전달하는 RAG 단계는 이 프로젝트에 구현하지 않았다. 생성 단계를 추가해야 검색 아이디어를 사용할 수 있는 것은 아니다. [RAG 원 논문](https://arxiv.org/abs/2005.11401).

| 적용 아이디어 | 현재 상태·남은 검증 |
|---|---|
| BM25와 E5의 상호 보완 | 직접 하이브리드 미실행; 같은 K에서 유입/탈락 확인 필요 |
| 여러 리뷰를 보존한 matching | 동결 Top-3·학습형 리뷰 late는 실행 완료; 토큰 단위 ColBERT 재현은 아님 |
| 속성별 근거·취향 분리 | 규칙 기반 10채널 정렬·K1/K3 취향 검색 완료; 품질 주석과 새 holdout 검증은 남음 |
| 실제 후보에 맞춘 hard-negative·리뷰 재정렬 | 과거 설계로 보존; 현재 retrieval 전용 후속에서는 보류 |
| 생성 설명의 근거 선택 | 미구현; 관련성·중복·순서와 사실성을 추천 정확도와 별도 평가해야 함 |

근거의 주제 관련성과 취향 방향은 다르다. 매운 음식 문서를 찾아도 안 매운 곳을 원하는 사용자에게 맞는 근거가 아닐 수 있다. 명시적 요청 검색과 과거 리뷰로 미래 방문을 추천하는 평가도 구분한다.

[ColBERT](https://arxiv.org/abs/2004.12832)는 여러 표현을 유지한 비교의 근거이고, [Lost in the Middle](https://arxiv.org/abs/2307.03172)은 생성 모델의 긴 근거 입력 위치에 관한 연구다. 두 논문을 현재 E5 평균 손실이나 한국어 식당 추천 개선의 증거로 해석하지 않는다. 완료한 추천 실험은 [RLMRec·리뷰 검색 리포트](./review_embeddings.md), 남은 데이터 조사는 [텍스트 데이터 조사](./text_data.md)에 구분해 둔다.
